# store_tool · 可靠性设计（Reliability Design）

> 本文档说明 store_tool 作为后端服务底座，在鉴权、数据、可恢复性、可观测性方面的可靠性设计。目标是让上层 AI 应用（如 swan_rag）跑在可信的工程底座上。

---

## 一、可靠性设计原则

1. **默认拒绝**：未授权请求在进入业务逻辑前被拒绝。
2. **统一错误契约**：所有异常收敛为同一信封，调用方不必猜测错误结构。
3. **Schema 可演进、可回滚**：数据库结构变化走版本化迁移，不依赖 `create_all` 临时兜底。
4. **可测试性即可靠性**：核心路径有 pytest 单测，回归靠测试而非记忆。

---

## 二、失败模式清单（FMEA）

| 编号 | 失败模式 | 触发场景 | 影响 | 现有兜底 |
|---|---|---|---|---|
| F1 | **未授权访问** | 缺 Key / 错 Key | 数据暴露 | 全局依赖 `get_api_key`，未带/错误一律 401 统一信封 |
| F2 | **请求参数非法** | 客户端传错字段/类型 | 业务不可达 | 全局 `RequestValidationError` → 422 统一信封（含 details） |
| F3 | **资源不存在** | 按 id 查门店/库存，已被删除或 id 错误 | 误判为成功或异常 | 每个读写路径先查存在性，不存在抛 404 统一信封 |
| F4 | **数据库连接失败 / 文件锁** | SQLite 文件被占用、磁盘满 | 请求失败 | 依赖注入统一管理会话（`get_session`）；启动 `init_db` 建表 |
| F5 | **批量查询部分失败** | 批量库存查询含非法 store_id | 部分结果不明确 | 查询逻辑对每项独立查库，不存在则返回 qty=0，不中断整体 |
| F6 | **Schema 漂移（迁移与模型不一致）** | 手动改库、迁移未执行 | 运行时报错 | Alembic 迁移作为 schema 唯一真相源；`alembic upgrade head` 幂等可回滚 |

---

## 三、兜底路径（按优先级）

| 层级 | 机制 | 说明 |
|---|---|---|
| **隔离** | 全局 API Key 鉴权 | 所有请求先过鉴权，非法调用被挡在业务外 |
| **契约** | 统一错误信封（`{error:{code,message}}`） | 调用方按 code 处理，不依赖解析散乱文本 |
| **一致性** | Alembic 版本化迁移 | 结构变更可追踪、可回滚，避免 create_all 漂移 |
| **可观测** | pytest 单测 + 统一响应 | 回归可自动化；线上错误结构可预期 |
| **恢复** | 幂等 seed + 可重建 db | 数据文件可删除重建，示例数据 seed 幂等可重复执行 |

---

## 四、长链任务状态管理（说明）

store_tool 当前为短事务型 CRUD（单请求内完成读写提交），无跨请求长链任务。若在其上构建多步 Agent 流程，可靠性扩展方向：

- 任务状态表（task_id / step / status / payload / created_at）
- 断点续跑（失败步骤重放，成功步骤跳过）
- 超时治理（每步超时 + 整体超时）
- 人机协同（关键节点人工确认）

该扩展已在现有工程结构（模型层/迁移/依赖注入）上预留落位。

---

## 五、与上层 AI 应用的关系

swan_rag 复用本仓库的工程底座（FastAPI + SQLModel + 鉴权 + 统一错误 + Docker），并在其上叠加：

- 启动自愈合（corpus 哈希比对，漂移即重建索引）
- 数据接地护栏（真相源 + pytest 一致性卡点）
- 评测闭环（golden-set 回归）

**后端可靠性是 AI 可靠性的地基**——没有统一的错误契约与可迁移的 schema，AI 应用的兜底与自愈都无从谈起。
